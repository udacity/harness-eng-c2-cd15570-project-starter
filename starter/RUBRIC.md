# Production Vehicle EDA Harness Rubric

### Project Rubric

| Criteria | Submission Requirements | Reviewer Tip |
|---|---|---|
| **Implement Foundational Orchestration** | <ul><li>Loop 01 loads relevant skills through the registered skill interface.</li><li>Loop 01 dispatches EDA actions only through the registered tool handlers.</li><li>Loop 01 pauses planned EDA actions after a plan approval request and resumes after approval.</li><li>Loop 01 records tool name, input, status, and output in the run log.</li><li>**Evidence:** `harness/stage_01_loops/loop_01_non_production.py`, `prompts/prompt_01_non_production.txt`, and a Loop 01 terminal log or `outputs/agent_tools.json`.</li></ul> | <ul><li>**Pass if:** the submitted run shows skills, planning, approval, and at least one EDA tool action through the shared loop.</li><li>**Fail if:** planned EDA actions run after a plan approval request but before user approval.</li><li>**Pass with comment if:** the implementation uses a different internal organization while preserving the registered tools and approval behavior.</li></ul> |
| **Evaluate Completed Runs** | <ul><li>Loop 02 starts retrospective evaluation only after the primary task reaches completion or its iteration limit.</li><li>The evaluator receives the original prompt, execution trace, tool-run log, task result, and final response.</li><li>The evaluator result contains `task_status`, `efficiency_score`, `critique`, `systemic_failure_root_cause`, and `workflow_adjustments`.</li><li>The completed run saves structured evaluation output to `outputs/retrospective_evaluation.json`.</li><li>**Evidence:** `harness/stage_01_loops/loop_02_self_evaluation.py`, `harness/stage_04_evaluation/retrospective_evaluation.py`, `prompts/prompt_02_self_evaluation.txt`, and `outputs/retrospective_evaluation.json`.</li></ul> | <ul><li>**Pass if:** the evaluation appears after the primary task and is separate from the primary answer.</li><li>**Fail if:** the result omits required fields or evaluates a task that remains paused for approval.</li><li>**Pass with comment if:** the evaluator uses a different valid JSON-validation approach and preserves the required artifact fields.</li></ul> |
| **Integrate Deterministic Controls** | <ul><li>Loop 03 invokes hook logic before or after registered tool execution without duplicating the foundational agent loop.</li><li>The antidote registry implements at least three deterministic checks for recurring tool failure patterns.</li><li>At least one antidote blocks an invalid request or returns deterministic chart evidence after a chart action.</li><li>The hook loop records hook or antidote activity in `state.tool_run_log` and returns the resulting evidence to the model observation.</li><li>**Evidence:** `harness/stage_01_loops/loop_03_hooks.py`, `harness/stage_05_antidotes/`, `prompts/prompt_03_hooks.txt`, and a Loop 03 tool trace.</li></ul> | <ul><li>**Pass if:** the trace shows a hook or antidote intervention caused by the Loop 03 prompt.</li><li>**Fail if:** the implementation only describes safeguards in a prompt and does not enforce or generate deterministic output in code.</li><li>**Pass with comment if:** the three checks address different recurring failures from the example patterns in the instructions.</li></ul> |
| **Enforce Scoped Permissions** | <ul><li>The permission policy returns explicit `allow`, `require_approval`, and `deny` decisions with a reason.</li><li>Read-only EDA actions receive an allowed decision.</li><li>`plot_data` and `rank_inventory` receive an approval-required decision.</li><li>Loop 04 pauses for a protected request, displays the requested tool and arguments, and resumes after user approval.</li><li>A grant executes only the exact approved protected request and is consumed after use.</li><li>**Evidence:** `harness/stage_06_permissions/policy.py`, `harness/stage_01_loops/loop_04_permissions.py`, `prompts/prompt_04_permissions.txt`, and a Loop 04 tool trace showing permission decisions.</li></ul> | <ul><li>**Pass if:** the trace shows an allowed action and separate approval-required actions for the plot and ranking.</li><li>**Fail if:** a protected call executes before approval or a changed request reuses an earlier grant.</li><li>**Pass with comment if:** the implementation presents the user decision differently while retaining a scoped request comparison.</li></ul> |
| **Produce Reproducible Evidence** | <ul><li>Four loop-specific prompt files exist with names from `prompt_01_non_production.txt` through `prompt_04_permissions.txt`.</li><li>Each prompt runs with its matching loop option and demonstrates the component added in that loop.</li><li>`outputs/` contains a completed answer, tool trace, retrospective evaluation JSON, and chart artifact from the submitted runs.</li><li>The written comparison identifies the added control, evidence source, and observed intervention for all four loops.</li><li>**Evidence:** `prompts/`, `outputs/agent_output.txt`, `outputs/agent_tools.json`, `outputs/retrospective_evaluation.json`, `outputs/plots/`, and the submitted comparison document.</li></ul> | <ul><li>**Pass if:** artifact names and contents connect each loop to its matching prompt and observed behavior.</li><li>**Fail if:** a required artifact is absent or the comparison does not cover all four loops.</li><li>**Pass with comment if:** output files use alternate names while the submission identifies their paths and preserves the required evidence.</li></ul> |

### Suggestions To Make Your Project Stand Out

| Criteria | Submission Requirements | Reviewer Tip |
|---|---|---|
| **Optional Extensions** | <ul><li>Add an ablation comparison in `reports/ablation_results.md` that measures quality and tool-use differences across loops.</li><li>Add a categorized failure log in `reports/failure_log.md` that maps repeated failures to controls and prevention rates.</li><li>Add cost and token accounting in `reports/cost_analysis.md` that compares component efficiency.</li><li>Add a data-quality scenario using `vehicle_sales_reviews.csv` and connect identified issues to an EDA limitation.</li><li>Add a permission test proving a changed protected request cannot consume a previous grant.</li></ul> | <ul><li>**Optional:** these extensions are not required for a passing submission.</li><li>**Praise if:** an extension produces new evidence or a meaningful control beyond the required loop behavior.</li></ul> |
